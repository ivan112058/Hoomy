# 0005 - 全库数据一次取回，不做增量分页 UI

日期：2026-09-10　状态：已接受

## 背景

「列出全部歌曲」需要决定加载策略。核实结论：`search3` 空 query 在 Navidrome 上按自然顺序返回全库并支持 offset 分页（OpenSubsonic 要求服务端支持空 query 返回全量，正是为离线同步设计）；但 `searchResult3` **不返回任何总数或页码字段**，终止只能靠空页或短页判断。实测曲库 908 首，`songCount=500` 时只需 2 次请求。

## 决策

进入歌曲 Tab 时**一次性取回全部页**（`songCount=500`，循环至短页），在本地完成分组、排序与搜索。

1. 分页仅作为**传输手段**，不作为 UI 概念：界面不显示「第几页/共几首」。
2. 字母分组、A-Z 快捷栏、搜索均在本地全量数据上计算。
3. 搜索为**本地纯内存过滤**，不调用服务端 `search3` 带 query 的检索。

## 后果

- 908 首约 2 次请求，滚动与搜索响应均为瞬时；实现比增量分页简单。
- 曲库显著变大（数万首）时此策略会退化：届时需改为增量加载，且因为响应无总数，「加载进度」只能显示为不确定态。
- 搜索能力受限于已取回的本地数据，无法搜索未加载的内容——这是选择「全量取回」的必然代价，在万首以内不构成问题。
