# 0012 - 队列持久化用普通键值存储，位置按播放位置节流落盘

日期：2026-09-14　状态：已接受

## 背景

用户故事 35 要求「关掉 App 再打开，队列还在（以暂停状态恢复）」。要落地需要定四件事：**存哪**、**存什么**、**什么时候存**、**存不进去怎么办**。与 ADR-0006（封面缓存策略）同属「本地持久化策略」类决策。

## 决策

1. **存普通键值存储（`shared_preferences`），不进安全存储。** 队列内容是歌名／歌手／专辑／时长／封面 id 等公开音乐元数据，不含凭据；只有凭据（`CredentialStore`）才需要 `flutter_secure_storage`。存完整曲目而非只存 id：重建队列不需要网络往返，离线也能显示「上次在听什么」。
2. **只存随机开关，不存本轮随机顺序。** 重启后无从知道上一轮随机实际走过哪些曲目、顺序如何，因此恢复时随机关闭就按队列自然序定位；随机打开就按「当前曲目 + 其余」重新开一轮 —— 与「播放中途打开随机」同一套规则。队列内容与当前曲目精确保留，代价是恢复后「已播放」段清空、其余顺序重洗。
3. **位置按播放位置的前进量节流（5 秒）落盘，暂停与 seek 时立即写。** 位置流本身就是节拍器，不需要墙钟定时器（也没有要清理的定时器）；强杀 App 最多丢约 5 秒。位置属于当前曲目：换歌时位置归零，绝不把上一首的位置写进新曲目的快照。
4. **持久化是尽力而为。** 读不出来（没存过／JSON 损坏／字段缺失／索引越界／存储不可用）一律当作没有可恢复的队列；写不进去静默放弃。任何一种情况都退化为空队列，不崩溃、不拦启动。格式不设版本号与迁移：结构不符即整份作废，恢复成空队列。

## 后果

- 恢复后处于暂停态，不自动播放；界面（迷你播放条、队列覆盖层）按持久化内容呈现。
- 随机模式下重启是「接着这首、换一套后续顺序」，不是逐首续播。
- 退出登录与切换服务器**不清理**持久化队列（MVP 只有单服务器单用户，多服务器在范围之外）。若日后支持多服务器，需按服务器隔离或在校验失败时丢弃。
- 队列里的曲目若已在服务端删除，恢复后加载会失败并走既有播放失败提示，不影响队列本身。
