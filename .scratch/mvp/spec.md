# Hoomy MVP 规格

状态：ready-for-agent　日期：2026-09-10

术语以 `CONTEXT.md` 为准；技术决策见 `docs/adr/`；服务端与第三方库的事实依据见 `docs/research/`。

## 问题陈述

用户的音乐库放在家里局域网的 NAS 上，由 Navidrome 提供。手机和电视上都没有一个趁手的客户端：

- Navidrome 自带的是网页界面，在 iPhone 上操作别扭，在电视上遥控器几乎没法用。
- 通用音乐 App 要么不认 Subsonic 协议，要么界面完全不是想要的样子。
- 用户明确知道自己要什么样的界面：锤子音乐 8.1.0 那种直角、白底、红色播放态、蓝色交互态的秩序感（参考 `SmartisanMusic-Revived`）。

结果就是：曲库（实测 908 首、218 专辑、128 歌手）能通过网页访问，但「躺在沙发上用电视听歌」和「用 iPhone 随手听歌」这两件事都做不到。

## 解决方案

一个 Flutter 客户端，用 Subsonic 兼容 API 对接 Navidrome，在 **iOS 与 Android TV** 上把「浏览曲库 → 播放 → 看歌词」这条链路做顺，并采用上述锤子音乐的视觉语言。

关键取舍：

- **客户端不解析音频文件**。metadata、封面、歌词全部取自服务端已解析的结果（ADR-0001）。
- **不做转码**，请求原始流（`format=raw`），交付 flac/mp3/m4a 原样数据。
- **不追求黑胶唱盘那类拟物交互**：播放页是静止封面（ADR-0003），歌词在播放页内与封面同层切换（ADR-0007）。
- 歌词按**内容档位**渐进呈现，而不是按服务端版本静态判断（ADR-0004）。

## 用户故事

### 服务器与登录

1. 作为用户，我想输入服务器地址、用户名和密码并登录，以便访问我 NAS 上的曲库。
2. 作为用户，我想在地址里省略 `http://` 也能登录，以便少打几个字。
3. 作为用户，我想在用户名或密码错误时看到明确的中文提示，以便知道是凭据问题而不是网络问题。
4. 作为用户，我想在服务器连不上时看到区分过的原因（超时／无法连接／地址不对），以便自己排查。
5. 作为用户，我想登录一次之后不用每次重输凭据，以便随手打开就能听。
6. 作为用户，我想在设置里退出登录并清除本机凭据，以便把设备交给别人时不留下我的密码。
7. 作为用户，我想只支持标准证书校验（不信任自签证书），以便不必处理证书信任这种危险操作。

### 浏览曲库

8. 作为用户，我想看到曲库里的全部歌曲，以便知道 NAS 上到底有什么。
9. 作为用户，我想按专辑浏览（封面网格），以便像翻唱片一样找歌。
10. 作为用户，我想按歌手浏览，以便顺着一个人听下去。
11. 作为用户，我想点进专辑看到它的曲目列表，以便整张听或挑一首听。
12. 作为用户，我想点进歌手看到他的专辑与全部歌曲，以便按人而不是按专辑找。
13. 作为用户，我想在歌曲行上看到歌名、歌手·专辑、时长，以便在列表里认出一首歌。
14. 作为用户，我想按下列表行时有整行变蓝、文字变白的反馈，以便知道自己点中了哪一行。
15. 作为用户，我想歌曲、专辑、歌手都按字母分组并带 A–Z 快捷栏，以便在几百首里快速跳到某一段。
16. 作为用户，我想在搜索框里输入就即时过滤本地已加载的歌曲，以便不用滑动找歌。

### 播放

17. 作为用户，我想点一首歌就开始播放，以便立刻听到声音。
18. 作为用户，我想看到当前播放的曲目与进度，以便知道放到哪了。
19. 作为用户，我想暂停与继续，以便临时中断。
20. 作为用户，我想拖进度条跳到任意位置，以便重听某一段或跳过前奏。
21. 作为用户，我想切上一首与下一首，以便换歌。
22. 作为用户，我想切换循环模式（关／全部循环／单曲循环），以便一首歌反复听或一张专辑循环听。

## 实现决策

### 数据层

- 继续用 `SubsonicClient` 作为协议层，**通过注入 `Dio` 暴露 HTTP 传输接缝**（见测试决策）。它负责生成认证参数（`u`/`t`=md5(password+salt)/`s`/`v=1.16.1`/`c`/`f=json`）、拼请求、解包 `subsonic-response` 信封、把 Subsonic 错误码转成领域异常。
- **全库取数**：歌曲列表用 `search3` 空 query，`songCount=500` 循环翻页直到短页或空页。响应中**没有总数与页码字段**，因此界面不得显示「共 N 首」。
- **不扩展**：搜索为本地内存过滤，不调用服务端检索。字母分组、A-Z 快捷栏、搜索索引都在本地全量数据上计算（ADR-0005）。
- 在协议层之上按功能建 repository（歌曲／专辑／歌手／歌单／风格／收藏／歌词），对上层暴露领域模型而非 API 原始结构。当前仓库中 `subsonicClientProvider` 被页面直接消费，需改为经 repository。
- 模型层补齐当前缺失的部分：专辑曲目与歌手曲目已能取到但未分层暴露；歌词需支持逐字档位（`cueLine`/`cue`）。解析须对字段缺失容错（不同服务端版本字段集不同）。
- **歌词档位由内容决定**：有逐字时间轴 → 逐字；仅行级 `start` → 逐行；无 `start` → 纯文本；无歌词 → 空态。`getLyricsBySongId` 无结果时回退 `getLyrics`（纯文本）。逐字的 `byteStart`/`byteEnd` 是 **UTF-8 字节闭区间**，按字节切片，不得按字符下标切。
- **封面缓存**：按 `coverArt` id 落盘，不设过期，失效仅靠设置页手动清除（ADR-0006）。缓存与清除逻辑集中在一处，界面不直接读写文件。

### 播放层

- 引入 **`PlayerEngine` 接缝**：一个只抽象「播放引擎」的接口（加载、播放、暂停、跳转、音量、播放位置与状态流、播放完成事件），其上是一个**纯 Dart 的播放状态机**，负责队列推进、循环模式、随机模式、当前曲目切换。队列规则必须能脱离音频设备测试（S2）。
- `PlayerEngine` 的默认实现基于 `just_audio`（ADR-0010）。`just_audio` 的 `Player` 不得被界面或状态机直接引用。
- **认证走 URL 查询串**，不使用 `httpHeaders`。`stream` 请求必须带 `format=raw`（不转码，ADR-0001）。
- **媒体会话**由 `audio_service` 承担，其 `AudioHandler` 是播放状态的权威持有者；`audio_session` 负责音频会话配置与打断处理（来电、其他 App 抢占、耳机拔出）。`media_kit` 不在本项目中使用（ADR-0010）。
- 已知且被接受的缺口：**iOS 的锁屏／控制中心在 MVP 内不工作**（ADR-0011）。后台继续播放是验收项，锁屏控件不是。
- TV 上的媒体键由系统经 `MediaSession` 路由，应用不自行分发；界面焦点层另作处理。

### 界面层

- 视觉约定（直角、按压变蓝且文字变白、列表行 60dp 无封面缩略图、分隔线 0.67dp 整宽、专辑固定 3 列、标题栏 50dp/20sp、浅色优先深色跟随系统）以 `CONTEXT.md` 的「视觉与交互约定」为准，当前主题实现需逐值对齐（ADR-0003）。
- 导航轴：一级底部 Tab（播放列表／艺术家／专辑／歌曲／更多）→ 其上常驻**迷你播放条** → 全屏播放页 → 队列覆盖层。迷你播放条显示封面、歌名、歌手与播放控制，**不显示进度**。
- 播放页：静止封面、可拖动进度条、五键中控（循环／上一首／播放暂停／下一首／随机）。点封面与歌词同层切换。
- **Android TV 的导航结构尚未决定**（侧边导航还是保留底栏待定），触屏专有交互（滑动删除、长按多选、拖拽排序）在 D-pad 上如何替代或砍掉亦待定。TV 上以聚焦／悬停反馈替代按压反馈。这两项不阻塞 iOS 首刀，但必须在 TV 布局切片前解决。
- 应用不做转码、不做音频文件解析、不下载整曲。

### 平台

- 目标平台**只有 iOS 与 Android TV**，优先级由高到低。macOS 与 Windows 已砍掉，对应的原生工程目录已删除。
- Android 只做 TV，不发布手机版、不做触屏手机布局。
- 验收设备：iPhone（真机，用于后台播放与格式验证）、Sony KD-55X9500G（BRAVIA 4K UR2，Android TV 10 = API 29）。

### 待办的前置修正（prefactoring）

- 关闭「结构化歌词解析不到」的既有缺陷（已修，纳入回归覆盖）。
- `streamUri` 已补 `format=raw`；确认没有其它端点遗漏了协议要求的参数。
- `songs_page` 当前的 200 首硬上限改为上述分页取全量。
- `main.dart` 已有登录态路由与主题接线，纳入回归覆盖。

## 测试决策

**好测试的标准**：只测外部行为，不测实现细节。断言「给定这组服务端响应，得到这个领域结果」，而不是「调用了哪个方法」。测试不应因内部重构而失败。

**一处接缝优先**：两个接缝都已开在最高点，且唯一。不引入 repository 接口抽象、不为封面缓存造接口——它们不值得第三个接缝。

- **接缝一（S1）：HTTP 传输。** 用固定响应测试 `SubsonicClient` 的完整链路：认证参数生成、请求组装、`subsonic-response` 信封解包、错误码到异常的映射、各端点的领域模型解析（含字段缺失、歌词三种档位、UTF-8 字节区间）。用 Dio 的 adapter 注入假响应，**不回放真实网络**。这是价值最高的接缝——既有缺陷（歌词解析路径错误、模型字段名错误、`format=raw` 缺失）全部落在这一层。
- **接缝二（S2）：`PlayerEngine`。** 队列推进、循环、随机、当前曲目切换、进度推进的规则用假引擎测试，**不依赖音频设备**。这是唯一能自动覆盖播放状态机的办法。
- **界面层**：widget 测试用 Riverpod 的 provider 覆盖注入假数据源（仓库中已有 `subsonicClientProvider.overrideWithValue(null)` 的先例），延续现有做法，不新增接缝。覆盖登录态路由、迷你播放条与播放页的呈现、歌词三种档位的渲染。
- **真实服务器集成测试**：保留 `test/live_server_test.dart` 的形态，**默认跳过**，需 `--dart-define` 传入服务器与凭据才运行（S3）。它测的是「真实 Navidrome 返回什么」，与接缝一的固定响应互补，且已被证明能抓出真实缺陷。只调用只读端点。
- **真机验收（无法自动化，手工检查项）**：iOS 后台播放；Android TV 上 flac 与 m4a 能否播放、seek 是否准；TV 遥控器媒体键；TV 上的焦点移动。这些写进对应票据的验收标准，不伪装成自动化测试。

## 范围之外

- **平台**：macOS、Windows、Android 手机。
- **砍掉的功能**：评分／星级、播放次数统计、睡眠定时、均衡器与音效、文件夹浏览、桌面歌词、歌词编辑与分享、倍速播放、跳过静音、交叉淡入、摇一摇／手势切歌、桌面小组件、投屏、Android Auto/CarPlay、标签编辑。
- **歌单的写操作**：新建、改名、删除、增删曲目（MVP 只读）。
- **搜索的进阶形态**：服务端搜索、搜索历史、搜索建议、按歌手／专辑分组的搜索结果页。
- **账户**：多服务器、多用户、账户切换。
- **认证的进阶**：自签证书信任、API Key 认证、明文密码兼容路径。
- **音频**：转码、码率限制、离线下载、回放增益。
- **收藏范围之外**：目前包含歌曲／专辑／歌手三个粒度，均不在 MVP 之后才做。
- **表格与 TV 待定项**：重新排序底部 Tab、「更多」页的自定义、TV 导航结构与其触屏交互替代方案。
- **歌词的进阶**：翻译／音译歌词（`kind` 为 translation/pronunciation）、多语言歌词选择、侧车文件的客户端管理。

## 补充说明

- **iOS 锁屏控制是已知缺口**，不是遗漏：`audio_service` 已发布版本在 iOS ≥ 13 不上报播放状态，修复已合并但未发版。本项目决定只用发布版依赖，因此不修（ADR-0011）。验收时不要把锁定屏控件计入 MVP 达标条件。
- **Android 的 flac 风险已降级但未清零**：目标电视是 Android TV 10（API 29），在 Media3 要求的 API 27 之上，所以不存在「设备解不了 flac」的问题；但 `just_audio` 有未修的 FLAC seek 偏差与解码错误 issue，是否在曲目上复现需真机验证。若证伪，回退手段是在 Android 侧挂 `just_audio_media_kit` 换用 libmpv 后端，Dart 侧代码不变。
- **服务端版本门槛**：结构化歌词需 Navidrome ≥ 0.51.0，逐字需 ≥ 0.63.0。实测服务器为 0.63.2。若用户换到更旧的服务端，歌词会自动降档，不需要改代码。
- **曲库规模实测**：908 首（769 flac / 116 m4a / 23 mp3）、218 专辑、128 歌手、23 风格、2 歌单、1 首已收藏。全部歌曲都有封面。全库取回约需 2 次请求。
- **开发用服务器**：`http://192.168.1.9:4533`（凭据见本机配置，不入库）。测试只调用只读端点，不调用 `star`/`unstar`/`scrobble` 等写端点。
